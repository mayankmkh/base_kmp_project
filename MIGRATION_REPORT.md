# Migration Report: CocoaPods to SwiftPM Import

**Project:** base_kmp_project
**Module migrated:** `:shared:app`
**Date:** 2026-08-14
**Kotlin version:** 2.4.10 → 2.4.10 (no change needed — already past 2.4.0-Beta2)
**Status:** Completed successfully, with a scope deviation — see *Non-Trivial Decisions #1*

> **Historical document.** Every path and Gradle task name below is as of 2026-08-14. The Helix
> adoption (phase 4, 2026-09-02) moved this module from `shared/app` to `app/shared`, so `:shared:app`
> is now `:app:shared` and `shared/app/…` is now `app/shared/…` — the Xcode build phase, for example,
> runs `./gradlew :app:shared:embedAndSignAppleFrameworkForXcode -i` today. Read the report for the
> reasoning, not for paths to copy.

---

## Scope deviation (read this first)

The `cocoapods {}` block in `:shared:app` declared **zero pod dependencies**. It was used purely as a
*publication* mechanism: it generated `SharedApp.podspec` so that `iosApp` could consume the Kotlin
framework via `pod 'SharedApp', :path => '../shared/app'`.

Consequently there was nothing to translate into `swiftPMDependencies {}` — that DSL declares
*consumption* of Swift packages, and this project consumes none. The migration performed is therefore:

> **CocoaPods-mediated framework delivery → direct framework integration via
> `embedAndSignAppleFrameworkForXcode`.**

No `swiftPMDependencies {}` block was added; an empty one would be dead configuration. See
*Non-Trivial Decisions #1* for how to add one later if a real Swift package is ever needed.

## Migration Steps

### Phase 2: Gradle Configuration

No changes required. Kotlin was already `2.4.10` (`gradle/libs.versions.toml:36`), well past the
`2.4.0-Beta2` minimum. The deprecated
`kotlin.apple.deprecated.allowUsingEmbedAndSignWithCocoaPodsDependencies` property was **not** present
in `gradle.properties`.

### Phase 3: swiftPMDependencies

**Not applicable** — no pods to consume. See *Scope deviation* above.

Phase 3.3 *was* performed: the framework configuration was moved out of `cocoapods { framework { … } }`
onto the targets' `binaries` API, and made static:

```kotlin
listOf(iosArm64(), iosSimulatorArm64()).forEach { iosTarget ->
    iosTarget.binaries.framework {
        baseName = "SharedApp"
        isStatic = true
    }
}
```

### Phase 4: Import Transformations

None. No `cocoapods.*` imports existed.

### Phase 5: iOS Project Reconfiguration

**Option: direct `.xcodeproj` integration** (the `.xcworkspace` existed only because CocoaPods
created it, so it was removed rather than kept).

1. Ran `integrateEmbedAndSign` (`XCODEPROJ_PATH=iosApp/iosApp.xcodeproj`,
   `GRADLE_PROJECT_PATH=:shared:app`) to add the Gradle build phase and linkage.
2. Corrected the `FRAMEWORK_SEARCH_PATHS` the task emitted — see *Error #1*.
3. Ran `pod deintegrate` in `iosApp/`, then removed the residue it left behind — see *Error #2*.
4. Deleted `iosApp/iosApp.xcworkspace/` and `iosApp/Pods/`.
5. Kept `ENABLE_USER_SCRIPT_SANDBOXING = NO` (it had been supplied by the podspec's `spec.xcconfig`;
   the Gradle build phase needs it).

```sh

  echo "Skipping Gradle build task invocation due to OVERRIDE_KOTLIN_BUILD_IDE_SUPPORTED environment variable set to \"YES\""

```

and, in both Debug and Release configurations:

```
FRAMEWORK_SEARCH_PATHS = (
    "$(inherited)",
    "$(SRCROOT)/../shared/app/build/xcode-frameworks/$(CONFIGURATION)/$(SDK_NAME)",
```

No Crashlytics dSYM script existed, so none needed repointing.

## Errors Encountered

### Error #1: `integrateEmbedAndSign` wrote a framework search path for the wrong module

**Phase:** 5
**Symptom:** The task wrote `$(SRCROOT)/../shared/build/xcode-frameworks/$(CONFIGURATION)/$(SDK_NAME)`
into `FRAMEWORK_SEARCH_PATHS`. The framework actually lives under `shared/app/build/…`.
**Root cause:** The task appears to derive the directory from only the **first segment** of the Gradle
project path. For `:shared:app` it used `shared` and dropped `app`. Any nested Gradle module hits this.
**Fix:** Rewrote both configurations' `FRAMEWORK_SEARCH_PATHS` to
`$(SRCROOT)/../shared/app/build/xcode-frameworks/$(CONFIGURATION)/$(SDK_NAME)`.
**Generalizable:** **Yes** — this will affect any project whose framework module is not a top-level
Gradle module. Worth an explicit check in the skill's Phase 5.

### Error #2: `pod deintegrate` left an empty `Pods` group in the pbxproj

**Phase:** 5
**Symptom:** After `pod deintegrate`, `project.pbxproj` still contained an empty `Pods` `PBXGroup`
(`755B6BDE944C60008193DD4A`) and the root group's reference to it.
**Root cause:** `pod deintegrate` removes build phases, file references and the workspace, but does
not always prune the now-empty group node it created.
**Fix:** Removed the group definition and its root-group reference. Verified with
`grep -niE "pods" project.pbxproj` returning nothing.
**Generalizable:** **Yes** — harmless to the build, but leaves confusing residue.

## Non-Trivial Decisions

### #1 — No `swiftPMDependencies {}` block was added

Adding an empty `swiftPMDependencies { iosMinimumDeploymentTarget = "16.0" }` was considered and
rejected: it declares no packages, so it configures nothing, and it would misleadingly imply the
project consumes Swift packages. The Kotlin tooling already runs its SwiftPM-import machinery for the
embed-and-sign path regardless (`generateSyntheticLinkageSwiftPMImportProjectForEmbedAndSignLinkage`
and `checkSyntheticImportProjectIsCorrectlyIntegrated` both execute on every iOS build).

**If a Swift package is needed later**, add to `shared/app/build.gradle.kts`:

```kotlin
@file:OptIn(org.jetbrains.kotlin.gradle.ExperimentalKotlinGradlePluginApi::class)

kotlin {
    swiftPMDependencies {
        iosMinimumDeploymentTarget = "16.0"
        swiftPackage(url = "…", version = "…", products = listOf("…"))
    }
}
```

and re-run `integrateLinkagePackage`.

### #2 — Compose resources were the main runtime risk, and are verified working

The deleted podspec carried `spec.resources = ['build/compose/cocoapods/compose-resources']`, i.e.
CocoaPods was responsible for getting Compose Multiplatform resources into the app bundle. A
successful *compile* would not have proven this still worked after removing CocoaPods.

Verified explicitly: on a clean build, Gradle runs `:shared:app:checkCanSyncComposeResourcesForIos`
and `:shared:app:syncComposeResourcesForIos` as part of `embedAndSignAppleFrameworkForXcode`, and
`arrow_back_24px.xml` (the project's only Compose resource, from `:shared:features:details`) lands in
`iosApp.app/compose-resources/`. Resource delivery is now owned by the Compose Gradle plugin rather
than by CocoaPods.

### #3 — `OTHER_LDFLAGS` was deliberately not restored

The Pods xcconfig had supplied `-l"c++" -framework "SharedApp"` (from the podspec's
`spec.libraries = 'c++'` and `vendored_frameworks`). These were not re-added by hand. A clean
from-scratch `xcodebuild` links successfully without them, so they were redundant once the framework
is linked through the target's Frameworks build phase.

### #4 — The `features.cocoapods` DSL knob was deleted, not renamed

An intermediate version of this migration renamed the convention-plugin knob to
`features.iosFramework` + `iosFramework.baseName`. That was reverted, because:

- the flag's only purpose had been to gate applying the CocoaPods plugin and to back a validation
  rule that asserted the plugin was applied — both meaningless once the plugin is gone;
- the convention plugin cannot eagerly read a flag the build script sets *after* the plugin applies,
  so honouring it would have required an `afterEvaluate` block just to create a framework binary;
- the framework config that matters (`export(...)`) is module-specific and cannot be centralised
  anyway.

The framework is now declared directly in `shared/app/build.gradle.kts` with a literal `baseName`.

### #6 — The framework switched from dynamic to static

The pre-migration framework was dynamic (`kotlin("native.cocoapods")` default, consumed via
`use_frameworks!`). It is now `isStatic = true`, per the skill's recommendation — dynamic frameworks
have known edge cases with the SwiftPM-import linkage path (linker errors, `dyld` crashes, duplicate
class warnings).

Consequences, all verified:

- The framework is **linked into the app binary** rather than embedded. `iosApp.app/Frameworks/` no
  longer exists, and `otool -L` shows no `@rpath/SharedApp.framework/SharedApp` entry — instead the
  Kotlin symbols live directly in `iosApp.debug.dylib`.
- Compose resources are no longer carried inside a `.framework` bundle; `syncComposeResourcesForIos`
  copies them to `iosApp.app/compose-resources/` instead. See *#2*.

### #5 — `.xcworkspace` was removed, not kept

`iosApp/iosApp.xcworkspace` existed only because CocoaPods generated it, and its
`contents.xcworkspacedata` referenced `Pods.xcodeproj`.

> **Action required for developers:** open `iosApp/iosApp.xcodeproj` from now on. Any IDE run
> configuration, CI job, or script still pointing at `iosApp.xcworkspace` must be updated.
